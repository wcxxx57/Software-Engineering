# Iteration4 推荐系统展示与实现验证说明

## 1. 文档目的

本文用于指导两类录制和验证：

1. **功能展示录制**：用网站页面讲清楚用户能看到什么、推荐内容如何切换、推荐内容和自己生成的内容有什么区别。
2. **实现验证录制**：在页面操作的同时，用 F12、接口响应和 PostgreSQL 查询证明固定知识点过滤、候选资格、排序、前三条截取、学习人数去重和计划状态门禁确实生效。

本文以当前本地运行版本为准，目标知识点为：

```text
curriculum_node_id = 65
节点标题 = 查找与排序
```

推荐展示的主线是“同一个知识点下有多个视频和 2D 候选，系统根据当前学习者的匹配程度和学习热度排序，页面只展示排名靠前的内容”。

需要特别区分三类功能：

| 入口 | 推荐对象 | 当前逻辑 | 是否个性化 |
| --- | --- | --- | --- |
| 学习任务页“知识视频” | `KNOWLEDGE_VIDEO` | 当前任务节点内过滤、排序，最多返回 3 条 | 是 |
| 学习任务页“2D 交互” | `INTERACTIVE_HTML` | 当前任务节点内独立过滤、排序，最多返回 3 条 | 是 |
| K2V/C2V/2D 独立工具页 | 精品目录资源 | `featured`、`PASSED`、公开、完成、有对象文件，再按 `display_priority` 和目录 ID 排序 | 否 |


## 2. 当前实现的准确口径

### 2.1 任务页候选资格

对当前用户打开的任务，后端先确认：

- 任务属于当前登录用户；
- 任务有 `curriculum_node_id`；
- 当前用户的课程模板与节点模板一致；
- 资源类型分别按 K2V 和 2D 分组；
- 资源目录的 `curriculum_node_id` 与任务节点完全相同；
- 资源目录状态为 `PASSED`；
- 底层资源为公开状态；
- 底层资源状态为 `FINISHED`；
- `object_key` 非空，且资源确实可以加载；
- 当前用户自己的资源留在“我生成的”区域，不作为自己的 peer 推荐候选。

因此，“标题都是查找与排序”不能代替节点 ID 检查；同名但节点 ID 不同的内容不应进入任务页推荐。

### 2.2 当前排序公式

每一个候选资源会收集资源创建者和已经打开过该资源的学习者，取其中与当前用户最接近的相似度作为该资源的 `similarity_score`。

当前最终分数为：

```text
popularity_score = min( ln(1 + 去重学习人数) / ln(9), 1.0 )

rank_score = similarity_score * 0.7
           + popularity_score * 0.3
```

排序顺序为：

1. `rank_score` 降序；
2. 分数相同时，去重学习人数降序；
3. 仍相同时，目录更新时间较新的优先；
4. 最后按 `catalog_id` 作为稳定排序依据；
5. 每一种资源类型只截取排名前 3 条返回给页面。

所以“有四个候选”与“页面只显示三个”并不矛盾：第 4 个候选仍然参与排序和调试核验，但不会进入页面轮换列表。

### 2.3 页面和 F12 中能看到什么

任务推荐接口返回两部分：

- `resources.knowledge_video` 和 `resources.interactive_html`：页面真正展示的前三条；
- `recommendation_debug`：全部通过候选资格检查的资源，包含完整排名和分数组成。

`recommendation_debug` 中的主要字段如下：

| 字段 | 含义 |
| --- | --- |
| `rank` | 在全部候选中的最终排名 |
| `selected` | 是否进入页面展示的前三条 |
| `rank_score` | 最终综合推荐分数 |
| `similarity_score` | 当前用户与候选关联学习者的最高相似度 |
| `popularity_score` | 去重学习人数带来的热度分 |
| `learner_count` | 去重后的学习人数 |
| `catalog_id` | 推荐目录记录 ID |

页面加载后，浏览器 Console 还会输出一个折叠分组：

```text
[推荐排序] task=任务 ID，展示前 3 个候选
```

展开后可以通过 `console.table` 同时查看视频和 2D 的全部排序候选。


## 3. 四个账号和任务页分工

四个账号不是重复执行同一件事，而是按“无候选 → 少量候选 → 两条候选可排序 → 多候选取前三”的顺序，逐步展示推荐系统如何从资源生成发展到排序推荐。

以下是当前本地数据快照。任务 ID 和资源 ID 属于当前数据库状态；如果重新创建计划或重置任务，应先查询重新确认，不要盲目沿用数字。

| 账号 | 当前任务页 | 节点 | 该账号在展示中的作用 | 页面要表达的核心情况 |
| --- | ---: | ---: | --- | --- |
| `rec_p1` | `/tasks/174` | 65 | 第一个内容生产者 | 当前知识点没有可推荐内容，直接自己生成视频和 2D，形成后续推荐的第一批内容 |
| `rec_p2` | `/tasks/187` | 65 | 第二个内容生产者 | 已经有 p1 生成的视频和 2D 可推荐；如果不满意推荐内容，可以在当前任务中自己重新生成 |
| `rec_p3` | `/tasks/209` | 65 | 第三个内容生产者 | 已经有 p1、p2 生成的视频和 2D 可推荐，按分数排序显示 `1/2`、`2/2`；不满意时也可以自己重新生成 |
| `rec_p4` | `/tasks/222` | 65 | 纯推荐观察者 | 后台已有 4 个视频和 6 个 2D 候选，页面按分数每类最多展示 3 条，验证大于 3 条候选时的截取和排序 |

四个账号都应使用独立浏览器无痕窗口或明确退出登录后再切换，避免 Cookie 串号。录屏时不展示密码、JWT、数据库密码、API Key 或生产域名。

### 3.1 `rec_p1`：没有推荐时，直接自己生成

打开 [p1 任务页](http://127.0.0.1:3080/tasks/174)。p1 代表“当前知识点暂时没有符合条件的可推荐内容”的起始状态，不需要先展示候选切换，而是直接从生成入口开始：

1. 确认任务标题为“查找与排序”；
2. 确认当前知识点没有可推荐的视频和 2D；
3. 点击“为当前知识点重新生成”或对应的生成入口；
4. 分别准备一个知识视频和一个 2D 交互内容；
5. 等待资源完成并回到任务页；
6. 展示生成后的中文标题、视频播放区或 2D 操作区。

这一段要表达的是：

> 当系统找不到当前知识点的合适推荐内容时，用户可以直接生成自己的学习资源。p1 生成的内容随后会成为 p2、p3、p4 可以看到的候选之一。

这里不要把 p1 的生成结果说成“推荐内容”；p1 的重点是建立第一批内容，证明没有候选时页面仍然可以继续学习。

### 3.2 `rec_p2`：看到 p1 推荐，也可以自己重新生成

打开 [p2 任务页](http://127.0.0.1:3080/tasks/187)。此时 p1 已经为同一个知识点生成了视频和 2D，因此 p2 首先看到的是 p1 的推荐内容：

1. 展示 p1 生成的视频推荐；
2. 展示 p1 生成的 2D 推荐；
3. 说明 p2 当前看到的是“推荐内容”，不是 p2 自己生成的内容；
4. 如果 p2 对推荐内容不满意，点击“为当前知识点重新生成”；
5. 分别生成 p2 自己的视频和 2D；
6. 生成完成后切换“推荐内容 / 我生成的”，确认两种来源可以区分；
7. 在推荐模式下可以继续点击“换一个”，在自己的生成模式下播放或操作自己的资源。

这一段要表达的是：

> 推荐内容可以直接复用，但推荐不是强制结果。用户不满意时，仍然可以针对当前知识点生成自己的版本；生成后的内容归入“我生成的”，不会被误认为系统推荐。

### 3.3 `rec_p3`：两个推荐候选按分数排序，并允许重新生成

打开 [p3 任务页](http://127.0.0.1:3080/tasks/209)。此时 p1 和 p2 都已经生成了同一知识点的视频和 2D，p3 看到两个推荐候选：

1. 视频推荐区显示 p1 和 p2 的两个候选；
2. 2D 推荐区也显示 p1 和 p2 的两个候选；
3. 因为 p1 对 p3 的相似度更高，且 p1 候选的浏览量更高，p1 的内容排在前面，标记为 `1/2`；
4. p2 的内容排在后面，标记为 `2/2`；
5. 点击“换一个”可以在 `1/2` 和 `2/2` 之间切换；
6. 视频切换和 2D 切换相互独立；
7. 如果 p3 对推荐内容不满意，也可以重新生成自己的视频和 2D；
8. 生成后切换到“我生成的”，确认 p3 自己的内容与 p1、p2 的推荐内容分开显示。

这一段要表达的是：

> 当候选从一条增加到两条时，系统开始体现排序差异。p1 因为当前学习者相似度更高、浏览量也更高，所以排在 `1/2`；p2 排在 `2/2`。用户仍然可以选择推荐内容，也可以重新生成自己的版本。

这里的 `1/2` 和 `2/2` 表示当前页面可切换的推荐候选顺序，不表示后台只有两个资源。如果当前数据库中已经加入了更多候选，应以 p3 录制时的 F12 调试结果为准；本段的展示重点是 p1/p2 两个主要推荐候选的排序关系。

### 3.4 `rec_p4`：多候选排序后只展示前三条

打开 [p4 任务页](http://127.0.0.1:3080/tasks/222)。p4 代表“当前知识点已经有较多符合要求、可以参与排序的推荐资源”的成熟状态：

1. p4 当前任务没有自己的视频和 2D，因此直接进入推荐展示；
2. 后台预先准备了 4 个同一知识点的视频候选；
3. 后台预先准备了 6 个同一知识点的 2D 候选；
4. 视频和 2D 都超过页面最多展示 3 条的限制；
5. 页面只根据分数展示排名前 3 条，不会把全部候选同时塞进页面；
6. 视频页面显示 `1/3`、`2/3`、`3/3`；
7. 2D 页面也显示 `1/3`、`2/3`、`3/3`；
8. 评分更高、相似度更高或浏览量更高的候选排在 `1/3`；
9. 相对浏览量较小或综合分数较低的候选排在 `2/3`、`3/3`；
10. 第 4 个视频和第 4–6 个 2D 不进入页面轮换，但仍可在 F12 的 `recommendation_debug` 中查看排名和分数；
11. 视频“换一个”和 2D“换一个”各自只在自己的前三候选中轮换。

这一段要表达的是：

> 当一个知识点下已经积累了较多合格资源时，系统不会把所有资源全部展示，而是先计算排序分数，再为每一类内容选出前三条。页面展示的是前三名，后台调试信息仍然保留全部候选，因此可以同时验证“候选池大于 3”和“页面最多展示 3 条”这两个规则。
